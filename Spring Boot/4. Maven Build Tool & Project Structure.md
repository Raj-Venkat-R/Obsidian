# REST — Representational State Transfer

- A guideline/architecture style for building APIs efficiently
- Most commonly used in modern tech
- Replaced **SOAP** which was slow and heavy
- REST solves SOAP's problems and makes API creation efficient

---

# Project Structure
```
src/
├── main/
│   ├── java/          → All your Java code lives here
│   └── resources/
│       ├── static/    → Static files (CSS, JS, images)
│       ├── templates/ → HTML files (only if using Thymeleaf)
│       └── application.properties → App configuration
├── test/              → Unit test cases (mirrors main package structure)
target/                → Auto-generated by Maven (bytecode .class files)
pom.xml                → Project details + all dependencies
mvnw                   → Maven wrapper (Mac/Linux)
mvnw.cmd               → Maven wrapper (Windows)
```

---

# application.properties

All application configuration is defined here.
Two formats available — same job, different syntax:
```properties
# application.properties
spring.application.name=demo
server.port=8081
spring.data.mongodb.uri=mongodb://localhost:27017/devshell
```
```yaml
# application.yaml
spring:
  application:
    name: demo
server:
  port: 8081
```

# Ports & IP Address

- **IP Address** = identifies the server (the building address)
- **Port** = identifies the specific service on that server (the flat number)

| Service | Default Port |
|---|---|
| Spring Boot (Tomcat) | 8080 |
| MongoDB | 27017 |
| React (Vite) | 5173 |

Multiple services run on the same machine on different ports.
`localhost:8080` = this machine, door 8080 where Spring Boot is listening.

# Monolithic vs Headless Architecture

| Term | Meaning |
|---|---|
| Monolithic | One project handles everything — frontend, backend, database logic |
| Headless / Decoupled | Backend is pure API, frontend is separate, they talk via HTTP |

## Monolithic
- Spring Boot serves HTML pages itself
- Uses Thymeleaf templating engine
- HTML files go in `resources/templates`
- Old school approach

## Headless — What DevShell uses
- Spring Boot = pure REST API, returns JSON only
- React = completely separate project, handles all UI
- They communicate via HTTP (Axios)
- Modern industry standard

| Part | Technology | Job |
|---|---|---|
| Backend | Spring Boot | Pure REST API, returns JSON |
| Frontend | React | Consumes API, handles UI |
| Communication | HTTP (Axios) | React calls Spring Boot endpoints |

**This is why DevShell has both a React dashboard and Node.js CLI — both consume the same Spring Boot API. Only possible with headless architecture.**

# resources Folder

| Folder | Purpose | Used in DevShell? |
|---|---|---|
| `static` | CSS, JS, images served directly | No |
| `templates` | HTML templates (Thymeleaf) | No |
| `application.properties` | App configuration | Yes |

For a pure REST API — `static` and `templates` are never used.

# target Folder

- Auto-generated by Maven when you build/run
- Contains `.class` files — compiled Java bytecode
- Never touch manually
- Always in `.gitignore` — never push to GitHub
- Same concept as `node_modules` in Node.js

## Why Bytecode?

| Step | What Happens |
|---|---|
| You write | `.java` file (human readable) |
| Maven compiles | `.class` file (bytecode) |
| JVM runs | Bytecode on any OS |

"Write once, run anywhere" — same `.class` file runs on Windows, Mac, Linux.

# Maven Wrapper (mvnw)

Generated automatically by Spring Initializr.

| File | Purpose |
|---|---|
| `mvnw` | Mac/Linux |
| `mvnw.cmd` | Windows |

Use instead of installing Maven globally:
```bash
./mvnw spring-boot:run     # Mac/Linux
mvnw.cmd spring-boot:run   # Windows
```

# pom.xml — Project Object Model

The most important file in a Maven project.

**Job 1 — Project Information**
- Name, version, group, artifact, description
- Everything filled in at start.spring.io ends up here

**Job 2 — Dependencies**
- All libraries your project needs
- Maven downloads them + their internal dependencies automatically
```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
```

| Node.js | Spring Boot |
|---|---|
| `package.json` | `pom.xml` |
| `npm install` | `mvn install` |
| `node_modules` | `~/.m2/repository` |

# Apache & Maven

- Maven created by **Apache Software Foundation** in 2004
- Apache also created **Tomcat** — the web server embedded inside Spring Boot

**Apache is involved twice in your project:**
- **Apache Maven** — builds and manages your project
- **Apache Tomcat** — serves your Spring Boot API on port 8080

# Maven Commands

| Command | What it does |
|---|---|
| `mvn compile` | Compile `.java` → `.class` only |
| `mvn test` | Run all unit test cases |
| `mvn package` | Compile + test + create `.jar` file |
| `mvn verify` | Compile + test + package + verify integration tests |
| `mvn install` | Everything in verify + save to local Maven repository |
| `mvn clean` | Delete `target` folder — fresh slate |
| `mvn spring-boot:run` | Compile + run the server |
| `mvn clean install` | Clean + fresh build |
| `mvn clean spring-boot:run` | Clean + fresh run |

## mvn clean — Why it exists

Old `.class` files very rarely don't get replaced during compilation.
This causes weird unexplained behavior — wrong output, old code still running.
`mvn clean` wipes `target` and forces a completely fresh build.
```bash
# When something is broken and you don't know why:
mvn clean install
```

Analogy: Like clearing browser cache when a website isn't loading correctly.

## mvn package — Output
```bash
java -jar target/demo-0.0.1-SNAPSHOT.jar
```
Runs your entire application from the bundled `.jar` anywhere.

## Maven Repositories

| Repository | What it is |
|---|---|
| Maven Central | Internet repository — millions of libraries |
| Local repository (`~/.m2`) | Cache on your machine |

When Maven sees a dependency in `pom.xml`:
1. Checks local `~/.m2` first
2. If not found → downloads from Maven Central
3. Saves to `~/.m2` — no re-download next time

## Practical Command Guide

| Situation | Command |
|---|---|
| Normal development | `mvn spring-boot:run` |
| Weird unexplained behavior | `mvn clean spring-boot:run` |
| Check for errors without running | `mvn compile` |
| Before deploying | `mvn clean package` |
| Check everything is correct | `mvn verify` |

# Key Takeaways
- REST replaced SOAP — modern standard for building APIs
- Monolithic = one project handles everything, Headless = frontend and backend are separate
- `application.properties` is where all app config lives — port, DB connection etc.
- IP address identifies the server, port identifies the specific service
- `target` folder = auto-generated bytecode, never touch or push to GitHub
- `pom.xml` = `package.json` of Java — project info + dependencies
- Maven wrapper (`mvnw`) = use Maven without installing it globally
- Apache created both Maven and Tomcat — both are used in your Spring Boot project
- `mvn clean` fixes most weird unexplained build errors
- Maven downloads dependencies from Maven Central, caches them in `~/.m2`
